# ADR 0015: 캐릭터 타임라인을 상세 조회 때 API 안 queue로 받아 시즌별 partition에 구간 교체로 저장한다

## 상태

채택. [ADR 0014](0014-api-postgresql-migrations-on-startup.md)가 붙인 PostgreSQL에 첫 업무 테이블을 더한다.

## 맥락

웹 표 행에 "이번 시즌 레이드 N회 클리어" 같은 시즌별 집계를 보이려 한다. 조회할 때마다 Neople 타임라인을 받으면 90일씩 나눠 여러 번 불러야 해서 너무 느리다.
Neople 타임라인 API는 한 번에 90일까지, `limit` 100개씩 `next`로 이어 받는다. 시각이 분 단위이고 행에 고유 ID가 없으며, 같은 분에 상자를 여러 개 열면 내용이 똑같은 행이 실제로 여러 개 생긴다. 호출 한도는 앱당 1초 1,000건이다.
API는 서버 한 대, 인스턴스 하나로 돌고, 캐릭터와 공용 아이템을 이미 프로세스 메모리에 캐시한다. 등록 캐릭터 목록은 없고 사용자가 조회한 캐릭터만 알 수 있다.

## 결정

- **수집 범위**: 중천 시즌 시작 2025-01-09 06:00(KST)부터 지금까지를 받는다. 이벤트와 아이템 모두 같고 2017년부터의 이력은 받지 않는다. 집계 대상이 시즌이라 그 전 이력은 쓸 곳이 없다.
- **테이블**: 1xx, 2xx, 3xx는 `timeline_events`, 4xx, 5xx, 55x, 6xx는 `timeline_items`에 둔다. 아이템 행이 훨씬 많고 시즌 단위로 읽고 버리므로 `timeline_items`만 시즌별 range partition으로 나눈다. 시즌마다 테이블을 손으로 만드는 대신 partition을 쓰면 조회는 한 테이블처럼 하고 지난 시즌은 partition 단위로 떼거나 지울 수 있다. 새 시즌 partition은 시즌 시작 전에 migration으로 더한다.
- **구간 교체**: 같은 내용의 행이 실제로 여러 개일 수 있어 내용 비교로 중복을 막을 수 없다. 받은 구간의 기존 행을 한 transaction에서 지우고 새로 넣는다. 같은 캐릭터의 교체가 겹치지 않게 캐릭터 단위 advisory lock을 잡는다.
- **수집 시점**: 캐릭터 상세 조회가 그 캐릭터의 동기화를 queue에 넣는다. 마지막 성공 뒤 1시간이 지난 경우만 Neople에서 받는다. 상세의 캐릭터 캐시와 같은 1시간이다.
- **처리 위치**: API 프로세스 안의 메모리 queue가 처리한다. 대기 중이거나 처리 중인 캐릭터는 합치고 동시 처리는 2개로 둔다. 별도 worker 프로세스를 두면 배포 단위와 queue 저장소가 늘어나는데, 인스턴스 하나에서는 얻는 것이 없다. API가 다시 시작하면 대기열은 사라지지만 다음 조회가 다시 넣는다.
- **주기 갱신 없음**: 등록 캐릭터 목록이 없고, 사용자가 다시 보지 않는 캐릭터를 계속 받으면 Neople 호출만 늘어난다. 집계는 사용자가 볼 때 1시간 이내로 맞으면 충분하다.
- **응답**: 상세 응답은 동기화를 기다리지 않는다. 처음 동기화하는 캐릭터는 구간마다 여러 번 불러야 해서 응답이 그만큼 늦어지기 때문이다. 클라이언트는 동기화 상태를 모르며, 나중에 읽는 API는 값이 있으면 주고 없으면 비워 준다.
- **실패**: 재시도 없이 실패 이유와 시각만 기록한다. 1시간 규칙이 마지막 성공 기준이라 다음 조회가 이어 받는다.
- **종료**: 진행 중인 동기화를 abort하지 않고 기다리지도 않는다. 끝나지 않은 구간은 transaction이 적용되지 않아 다음 동기화가 그 구간부터 다시 받으므로 따로 정리할 상태가 없다. 대기열은 버리고 Prisma client를 닫는다. Prisma client는 닫은 뒤에도 다음 query에서 다시 연결하므로, 대기열을 남기면 종료 뒤에도 프로세스가 대기 캐릭터를 계속 받는다.

## 결과

- 처음 보는 캐릭터의 집계는 첫 조회 직후에는 비어 있고, 동기화가 끝난 뒤부터 나온다.
- 상세 조회를 하지 않은 캐릭터는 저장되지 않는다. 등록 캐릭터의 주기 갱신이 필요해지면 새 ADR로 정한다.
- API 인스턴스를 여러 개 띄우면 queue가 인스턴스마다 따로 있어 같은 캐릭터를 동시에 받을 수 있다. Neople 호출이 겹치고, advisory lock은 구간 하나의 교체만 직렬화하므로 먼저 시작한 쪽이 나중에 저장하면 `synced_until`이 뒤로 갈 수 있다. 행은 다음 동기화가 그 위치부터 다시 받아 맞춘다. 이 결정은 인스턴스 하나를 전제로 한다.
- 종료 직전에 받던 구간은 프로세스가 끝나기 전에 저장하지 못하면 다시 받는다. 진행 중인 동기화가 다시 연결한 DB 연결은 idle로 남아 있다가 닫히므로, 동기화가 끝난 뒤 프로세스 종료가 늦어질 수 있다. 첫 동기화 도중 끝나면 앞 구간부터 저장한 데까지는 남는다.
- 시즌이 바뀌기 전에 partition migration을 잊으면 새 시즌 아이템은 마지막 partition(`MAXVALUE`까지 열림)에 들어간다. 그 뒤에는 범위를 나누기 전에 행을 옮겨야 한다.
- 1년 넘은 이력을 Neople이 계속 주는지는 확인하지 않았다. 운영 배포 뒤 운영 DB에서 확인한다(#1180).
